LESSON 2: EXERCISES
==================

TIER 1: OBSERVE (CORE)
---------------------

1. Build and run hello.asm. Expected: the 26-byte message described in
   lesson.txt and status 0.

2. Use this exact declaration:

       message db "AB", 13, 10

   Keep message_length equ $ - message. Predict its value, then run.
   Remove 13,10 and observe how the next terminal prompt is positioned.

TIER 2: EXPLAIN (CORE)
---------------------

3. With the original message restored, temporarily REPLACE the final
   XOR ECX,ECX with:

       mov ecx, dword ptr [rsp+28h]

   On a successful write, expect status 26. This reads the API's output
   DWORD. Reading EAX instead would read a BOOL, not the byte count.
   Restore the original exit setup after the observation.

4. Draw the complete 38h reservation. Mark the bytes actually written by
   WriteFile through R9, the fifth argument, and each unused region.
   Explain why storing the fifth argument at [rsp+28h] would be wrong.

5. Explain how these differ:

       lea rdx, message
       mov al, byte ptr [message]

   Which yields an address, and which reads memory? Why does the first
   instruction not need to know the length of message?

6. GetStdHandle returns a handle in RAX. Why is MOV RCX,RAX enough to pass
   it to the next call, but not enough to preserve it across that call?

TIER 3: APPLY (OPTIONAL)
-----------------------

7. Add a second message and make two successive WriteFile calls. Use
   std_out as described in lesson.txt to preserve the handle. Obtain it
   once and reload all arguments for each call. Do not introduce a loop
   or another procedure yet.

   Expected output:
       Hello from x64 assembly!
       Second message.

   Both lines end with CRLF; the two byte counts match their declarations.

8. Move the message declarations to .const. Explain why printing still
   works but writing to those message bytes would not be allowed.

Keep exercise variants separate or restore hello.asm's original message
and exit status when finished.
