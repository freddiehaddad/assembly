STACK ALIGNMENT AND FRAME PLANNING
=================================

Scope: fixed-size Windows x64 frames using eight-byte register PUSHes.
Large allocations, dynamic allocation, and their stack probes are later
topics. A source comment or a small sketch is enough for these frames.

START WITH TWO DIFFERENT RSP VALUES
----------------------------------

    Caller immediately before CALL:  RSP = 1010h (multiple of 16)
    Callee immediately after CALL:   RSP = 1008h (8 modulo 16)

CALL subtracts eight and writes the return address at the new [rsp].
That address occupies [rsp] through [rsp+7]. It is already on the stack;
do not allocate it again when computing SUB RSP.

The Windows x64 executable entry point follows the same entry convention.
The absolute address varies; the alignment contract does not.

RESERVING MEMORY DOES NOT INITIALIZE IT
--------------------------------------

SUB RSP, N reserves N bytes below the old RSP. New RSP points at the
lowest-addressed byte of that reservation. Positive offsets refer to higher
addresses. There need not be a pushed value or initialized local at [rsp].

Windows has no red zone for temporary storage below RSP. Reserve space
before writing it. ADD RSP, N releases it; it does not erase the bytes.

THE PLANNING METHOD
-------------------

1. Write the procedure's input, output, and preservation contract.
2. List values that must survive calls; choose registers or local slots.
3. Count saved-register PUSH bytes as P (eight times the register count).
4. Calculate storage S for the outgoing call area and locals:
       20h shadow space if making calls
       8 bytes for each argument beyond the fourth in the largest call
       local variables, including any gaps for their own alignment
5. Choose the smallest allocation N >= S such that:

       (P + N) modulo 16 = 8

   Equivalently, (8 - P - N) modulo 16 = 0 at a call site.
   Padding = N - S. The entry return address is not part of P or N.

6. Draw offsets from RSP AFTER the PUSHes and SUB. Keep RSP fixed in the
   body, set up each call in the same outgoing area, and reverse your
   prologue at every returning exit.

For arbitrary S, padding is the nonnegative remainder of (8 - P - S)
divided by 16. Do not use an "even versus odd" shortcut.

SMALL EXAMPLES
--------------

    Saved registers   P     Storage S                         N     Padding
    0                 00h   20h shadow                        28h   08h
    1                 08h   20h shadow                        20h   00h
    2                 10h   20h shadow                        28h   08h
    0                 00h   20h shadow + 8-byte arg 5          28h   00h
    0                 00h   20h shadow + arg 5 + 8-byte local  38h   08h
    1                 08h   20h shadow + arg 5 + two DWORDs    30h   00h

One PUSH toggles the alignment by eight; two PUSHes restore the original
remainder. PUSH alone does not provide the outgoing shadow space.

A DWORD local requires four bytes, not a mandatory eight-byte slot.
Lessons 2-3 use an eight-byte slot for clarity. If the storage is instead
2Ch bytes with no PUSHes, N is still 38h: the padding is 0Ch bytes.

LAYOUT RULES VERSUS CHOICES
--------------------------

The ABI fixes the outgoing shadow and stack-argument locations at calls.
Local/saved-register placement and unused padding are design choices,
subject to alignment and unwind rules. Padding is not required to sit next
to a return address. Nor do all procedures need a frame or a saved RBP.

Do not PUSH registers halfway through a fixed-frame body and keep using
old offsets. Either include saves in the prologue or redesign the layout
and account for the new RSP at every access and call.
