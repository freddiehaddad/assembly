WINDOWS x64 CALLING CONVENTION
=============================

Scope: the standard Windows x64 ABI, with integer and pointer parameters.
These rules apply to our procedures and Windows API calls alike. They are
software contracts, not extra behavior performed by the CALL instruction.

ARGUMENTS AND RETURN VALUES
--------------------------

For the integer/pointer signatures used in these lessons:

    Argument position    Location before CALL
    1                    RCX
    2                    RDX
    3                    R8
    4                    R9
    5                    [rsp+20h]
    6                    [rsp+28h]
    7                    [rsp+30h]

Use the width of the parameter type: a DWORD uses ECX/EDX/R8D/R9D; a pointer
or HANDLE uses the full 64-bit register. A stack parameter slot is eight
bytes; not every parameter's value requires all eight bytes.

Scalar integer/pointer results use RAX, or EAX for a 32-bit result.
WriteFile returns a 32-bit BOOL in EAX, not a byte count. Its fourth argument
points to a separate DWORD output variable.

Floating-point parameters use XMM registers according to argument position;
scalar floating-point results use XMM0. Variadic functions, aggregates, and
vector calling conventions require additional rules outside these lessons.

SHADOW SPACE AND OWNERSHIP
-------------------------

Before CALL, the caller provides at least 20h (32) bytes:

    [rsp+00h .. rsp+1Fh]  four eight-byte home slots
    [rsp+20h ..]          fifth and later arguments, if present

The callee owns the home slots for the duration of the call. It may store
register arguments there or use them as scratch storage. The caller must
not keep values it needs after the call in these slots.

The slots are required even for a zero-argument function. They are not
automatically initialized, and CALL does not copy registers into them.
The caller supplies them so that every callee has the same known layout.

Reserve enough outgoing space for the largest call in a fixed-size frame.
Reuse it for successive calls; do not reserve another 32 bytes after every
return. Extra stack arguments follow the home slots in increasing argument
order. Their final locations matter, not the order of the MOV instructions
that fill them. Do not insert padding between these argument slots.

PRESERVING REGISTERS
-------------------

    Volatile integer registers:     RAX, RCX, RDX, R8-R11
    Nonvolatile integer registers:  RBX, RBP, RSI, RDI, R12-R15, RSP

"Volatile" means a callee is allowed to change the value, not that every
callee necessarily will. If a value must survive a call, keep it in your
own local storage or in a nonvolatile register whose incoming value you
preserve. MOV RCX, RAX does not preserve a handle across another call:
both registers are volatile.

A returning callee saves/restores only the nonvolatile registers it changes.
It must undo its own stack allocation and saves before RET. RET then removes
the return address; the caller remains responsible for its own allocation.
Neither party deallocates the other's frame.

For SIMD registers, XMM0-XMM5 are volatile and the low 128 bits of XMM6-XMM15
are nonvolatile. Wider vector state has additional rules; see the source
reference rather than extending the integer rules by analogy.

CALL, RETURN, AND ALIGNMENT
--------------------------

At a normal call site, RSP must be a multiple of 16. CALL pushes an eight-byte
return address, so the callee's entry RSP is 8 modulo 16. This also describes
the Windows x64 executable entry point used in these lessons.

After a frame-function prologue, keep RSP aligned and fixed in the body.
Our simple unwind-leaf procedures change neither RSP nor nonvolatile
registers and may run with the entry alignment.

The CPU does not reserve shadow space or choose padding. See
stack-alignment.txt for the calculation, including PUSH instructions.

PROLOGUES AND UNWIND INFORMATION
-------------------------------

A fixed-frame example with one saved register and no stack arguments:

    example proc frame
        push rbx
        .pushreg rbx
        sub rsp, 20h
        .allocstack 20h
        .endprolog

        ; Body: outgoing shadow space is [rsp+00h .. rsp+1Fh].
        ; Calls may use RBX without changing our saved incoming value.

        add rsp, 20h
        pop rbx
        ret
    example endp

PROC FRAME and the dot-directives produce unwind metadata for Windows and
debuggers; they do not execute instructions or allocate more memory.
The annotations must match the actual PUSH and SUB operations. An unwind
leaf such as Lesson 3's string_length needs no such annotations.

RBP is not required for these fixed-size frames. Saving via MOV into frame
slots is also possible; PUSH-first is a convenient teaching pattern, not
the only ABI-conforming layout.
